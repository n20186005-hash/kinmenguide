# Kinmen Guide｜單景點詳頁結構與驗收模板 v1.1

**適用範圍**：`kinmenguide.com/attractions/*/` 的既有頁面與未來新增景點。  
**示範**：`/attractions/zhaishan-tunnel/`。  
**基準**：以既有 v1.0 六層骨架為基礎，2026-11-03 按編輯要求更新為「訪客 FAQ 之後保留原有深度專題」及「關於景點內明列現行管理者」。  
**目的**：資料可信、內容不遺失、視覺順序一致、同一模板可遷移至每個景點。

## 一、固定呈現順序（桌面與行動版一致）

| 順序 | 模組 | 語意層級 | 關鍵要求 |
|---|---|---|---|
| 0 | 全站導覽、麵包屑 | 導覽 | 保留原網站導航 |
| 1 | 標題、副標題、時間/費用資訊、地圖/加入行程 | H1 + 輔助資訊 | 一頁一個 H1；非即時狀態不可宣稱「正在開放」 |
| 2 | 主實景圖與合法授權署名 | figure | 不得用其他景點代替或刪除署名 |
| 3 | 探索景點 | H2 | 2–3 段現場與用途說明，不虛構第一人稱走訪 |
| 4 | 遊覽建議 | H3（隸屬探索） | 交通、照明、天候、親子等精簡條列 |
| 5 | 景區特色 | H3（隸屬探索） | 3–5 項可查核賣點 |
| 6 | 關於〔景點〕 | H2 | **第一內容區末尾**，背景、歷史與**目前管理單位的完整名稱和官方證據連結** |
| 7 | 基本資料 | H2 | **緊接「關於」後**；管理單位亦設固定欄位 |
| 8 | 交通方式 | H2 | H3：開車、大眾運輸、交通查詢 |
| 9 | 路線地圖 | H2 | 入口與位置、開放參觀動線；無 GPX 不編造 |
| 10 | 人文生態 | H2 | 人文、建築/工程、地形地貌、動植物（有可信證據才顯示）、詳細特色 |
| 11 | 景點相冊 | H2 | 實景照片與署名；沒有多張已授權圖片時維持單圖 |
| 12 | 遊客資訊與常見問答 | H2 | 問答與資料源一致，FAQ Schema 應與可見問答對應 |
| 13 | **現地遊覽與行程延伸** | **H2 + 各主題 H3** | **保留既有文章的各項深度主題，必須放在 FAQ 後、周邊推薦前** |
| 14 | 周邊景點與順路行程 | H2 | 保留原站內鏈結並解釋地理關係，勿以同區等於步行可達 |
| 15 | 查核日期、資料來源與編輯說明 | H2 | 官方來源、日期、獨立第三方聲明、勘誤途徑 |
| 16 | 地區餐飲、住宿、其他推薦及頁尾 | 組件 | 不破壞既有整站共用組件 |

「第一屏」指從標題到「關於景點」的**第一個完整內容區**，不是限制要塞入裝置的單個視窗高度。

### 深度內容位置規則

保留舊文的獨立主題，不得因為模組化就刪掉有獨立資訊量的內容。**段落先從舊文搬移並核實，再新增補充**。對翟山坑道而言，`遊客資訊與常見問答` 後面，固定出現以下六個 H3：

1. 出發前怎麼查開放？
2. 值得停下來看的風景
3. 怎麼排進一天
4. 拍照、親子與雨天
5. 從戰時運補，看見坑道的尺度
6. 已結束的活動公告

它們共同位於 `## 現地遊覽與行程延伸` 之內，之後才是 `## 周邊景點與順路行程`。其他景點的主題應依景點類型決定，不硬套以上六個標題；但**延伸內容的位置不得改變**。

## 二、管理單位是「關於」必備資訊

- `operator.name`：現行單位的**完整官方名稱**，例如「內政部國家公園署金門國家公園管理處」。
- `operator.url`：官方管理機關該景點頁，或當前可確認其管理關係的官方公告。頁面「關於」內呈現可點擊的「目前管理單位」欄。
- 「基本資料」再提供「管理單位」短資料列，方便旅客掃讀。**管理單位不是 Kinmen Guide**，也不等於照片攝影者、一般旅遊推廣方或協作夥伴。
- 若尚未確定，應記錄「管理單位待查」於工作底冊，**不可猜測**；未核實前不得標為 QA 通過。
- 來源查核日隨個別頁面紀錄，權責發生移轉時重新查證並更新連結。

## 三、可重用內容資料契約

模板必備欄位（示例、非完整 TS 類型）：

```yaml
slug: "景點英文路徑"
title: "景點正式名稱"
subtitle: "一句話介紹"
heroImage: { path: "合法本地實景照", alt: "實景描述", credit: "署名／授權" }
paragraphs: [ "探索景點的真實描述" ]
advice: [ "3–5 個可操作的建議" ]
features: [ "3–5 個具體特色" ]
about: "景點背景、歷史與地理意義"
operator: { name: "現行管理單位", url: "直接官方來源" }
facts: [ { label: "管理單位", value: "同 operator.name" } ]
transport: { driving: "", public: "", lookup: [] }
map: { locationUrl: "", entrances: [], verifiedRoute: null }
heritage: { humanities: "", engineering: "", landforms: "", flora: null, fauna: null }
gallery: []
faq: []
deepDive: [ { title: "深度主題", paragraphs: [] } ] # 在 FAQ 後統一呈現；每站標題可不同
related: []
sources: []
lastReviewed: "YYYY-MM-DD"
```

目前站點代碼以 `src/data/attraction-detail-pilots.ts` 放置首站示範資料，並由 `src/components/AttractionOverview.astro` 產生第一內容區與基本資料；長篇內容在 `src/content/attractions/{slug}.md`。未來可將深度主題結構化，但需先確保現有 Markdown、共用側欄和 FAQ 功能不回歸。

## 四、內容遷移與站內 SEO 保護

1. 比對原頁所有 H2/H3、段落、內部連結、圖片與授權資訊，建立**搬移對照**，未經編輯批准不得刪除原有有價值的內容。
2. 歷史年份和技術尺度如來源互有矛盾，使用有根據的概括年份或註明官方差異；不得混寫。
3. 保留原網址、canonical、唯一 H1、meta description、麵包屑、`TouristAttraction`、`Article`、可見 FAQ 與 `FAQPage` 的一致性。
4. 動態開放時間、車次與費用需註明為一般資訊；不得虛構今天營運狀態、實時評價、訪客見證或個人實訪。
5. 圖片需有授權，輪椅/推車等可達性不能由單一設施推論全程可達。
6. 景點資料來源引用管理機關、金門觀光旅遊網等；官方公告如已過期，保留日期與歷史語境。
7. 保留加入行程、餐飲/住宿關聯、FAQ、頁尾與既有站點功能。新模板只能 opt-in 指定景點，禁止誤改其他集合。

## 五、工作交接與驗收

- **Sol（實作）**：較複雜的 Astro 元件、模板、型別、Build、Playwright/E2E、GitHub 分支與 PR。
- **Luna（核對）**：景點官方來源、現行管理單位、交通時段、圖文授權、原文搬移對照與 SEO 內容審查。工作複雜時由主 Agent 調整配置。
- **主 Agent（整合）**：核對內容與程式的一致性、逐項驗收、更新 `docs/attraction-template-migration.csv`、交接下一站。只有實際調用及取得結果才能標示子 Agent 已驗證。
- **一站一分支、一站一 PR**；跨新對話以 GitHub PR、提交 SHA、查核日期與 CSV 狀態接力，不以聊天訊息代替可追溯紀錄。
- **必須通過** `pnpm validate`、`pnpm test:browser` (desktop/mobile)、實際正式網址檢查後，才能標示 `VERIFIED`。CI 通過 **≠** Cloudflare 已部署。
- 版面測試：同頁只有一個 H1；「關於」為第一內容區最後、下一節必是「基本資料」；FAQ → 深度文章 → 周邊；「目前管理單位」真實來源可點擊；原有主題不遺失；圖片、內鏈與手機版無橫向溢出。
- 已上線頁面若再次改版，狀態改為 `IN_REVIEW`，新版本上線及複測後才能恢復 `VERIFIED`。
